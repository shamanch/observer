# Witness

**Проверяет, что AI-агент реально сделал задачу.**

Агент говорит «готово», а фича не работает — потому что тестов не было, а слово модели
проверить нечем. Witness превращает задачу в утверждённые человеком критерии приёмки
и прогоняет их детерминированно: HTTP-запросы, pass/fail, отчёт, публичный badge.

Без API-ключей. Без Docker. Без зависимостей. Всё остаётся в вашем репозитории.

```
witness init
witness claim "Добавить экспорт отчёта в CSV на странице /reports"
# ... агент работает ...
witness run
```

## Что происходит

1. **claim** — задача превращается в 3–7 проверяемых критериев. Утверждает их **человек**, а не модель.
2. **run** — каждый критерий исполняется детерминированно. Никакой второй LLM в роли судьи.
3. **ledger** — прогоны складываются в SQLite (`.witness/witness.db`) и живут в git: дальше это регрессионный набор.
4. **badge** — сертификат в README + `badge.json` с хешем ledger, который можно проверить.

## Установка

Нужен Node.js 24+ (в нём уже есть встроенное выполнение TypeScript и `node:sqlite`).

```bash
git clone https://github.com/shamanch/observer.git
cd observer
node bin/witness.js --help
```

Глобально из npm:

```bash
npm i -g witness-cli
```

Или разово, без глобальной установки:

```bash
npx witness-cli --help
```

Для локальной разработки из клона:

```bash
npm link
```

## Быстрый старт (5 минут)

```bash
# 1. в своём проекте
witness init

# 2. критерии приёмки — правится и утверждается человеком
witness claim "Экспорт отчёта в CSV на /api/export"

# 3. после работы агента
witness run

# 4. доказательство
witness report      # .witness/report.html — один файл, без сети
witness badge       # .witness/badge.svg + badge.json
```

Если приложение на другом порту — поправьте `baseUrl` в `.witness/witness.json`.

Готовый пример: [`examples/shop`](examples/shop/README.md).

## Команды

| Команда | Назначение |
|---|---|
| `witness init` | создать `.witness/`, идемпотентно |
| `witness claim "<задача>" [--yes]` | критерии приёмки; `--yes` для CI |
| `witness run [--all] [--claim <id>]` | прогон и запись в ledger |
| `witness run --baseline` | зафиксировать базу **до** работы агента |
| `witness report` | самодостаточный HTML-отчёт |
| `witness badge [--verify]` | сертификат для README и его проверка |
| `witness wrap -- <команда>` | запустить агента и сразу проверить |

Флаги: `--json`, `--base-url <url>`, `--no-tamper`, `--no-llm`, `--dry-run`.

## Скилл для агента

Чтобы агент проверял себя сам, перед словом «готово», установите навык:

```bash
# OpenCode
cp -r skills/witness ~/.config/opencode/skills/

# Claude Code
cp -r skills/witness ~/.claude/skills/
```

Навык требует: человек утвердил критерии, `witness run --baseline` снят до работы,
а после работы — свежий `witness run` с exit 0. Агенту запрещено ослаблять критерии
и считать ручные шаги доказательством. Для каталога aitmpl навык лежит в
`skills/witness/SKILL.md` (категория `development`).

## Три механики, которые отличают это от «ещё одной проверки»

**① Детерминизм.** LLM участвует один раз — при генерации критериев, с подтверждением человеком.
Дальше это обычные HTTP- и браузерные утверждения: воспроизводимо, дёшево, не деградирует вместе с моделью.

**② Differential.** Критерий обязан падать на базовой версии. Если он зелёный и до работы агента —
это тавтология, а не доказательство. `witness run --baseline` до задачи, `witness run` после.

**③ Anti-tamper.** Агент мог «починить» проверку вместо кода: удалить assertion, поставить `skip`,
добавить `--no-verify`, ослабить CI. Всё это попадает в отчёт отдельным списком.

## Модель критерия

```json
{
  "id": "csv-export",
  "text": "Экспорт отдаёт CSV с заголовками",
  "required": true,
  "check": {
    "type": "http",
    "method": "GET",
    "path": "/api/export",
    "expect": {
      "status": 200,
      "header": { "content-type": "text/csv" },
      "bodyContains": ["id,name"],
      "bodyMinLines": 2
    }
  }
}
```

Для JSON-ответа:

```json
"expect": {
  "status": 200,
  "header": { "content-type": "application/json" },
  "jsonNonEmpty": true
}
```

`jsonNonEmpty` проверяет, что в ответе есть **непустой** список, а не просто символ `[`.
`bodyMinLines` считает непустые строки — так CSV-критерий требует заголовок и хотя бы одну строку данных,
а не «в теле есть перевод строки».

`check.type` бывает три:

- `http` — запрос и сравнение статуса, заголовков или тела (включая `jsonPath`, `jsonNonEmpty`, `bodyMinLines`);
- `browser` — открыть страницу в Chromium, при необходимости кликнуть/заполнить и проверить видимость, текст, ошибки консоли;
- `manual` — шаг для человека; в отчёте помечается `РУЧНАЯ` и не влияет на exit-код.

Файлы лежат в `.witness/claims/*.json` — их можно править руками.

### Браузерная проверка

```json
{
  "type": "browser",
  "path": "/reports",
  "steps": [{ "action": "click", "selector": "#export" }],
  "expect": { "visible": [".toast"], "text": ["Готово"], "consoleErrors": "none" }
}
```

Playwright не входит в зависимости: он нужен только если у вас есть `browser`-критерии.

```bash
npm i -D playwright
npx playwright install chromium
```

Без него такие критерии получают статус `error` с этой же подсказкой — молча зелёными они не станут.
Цена честная: браузер ~300 МБ и запуск заметно дольше HTTP-проверки. Поэтому шаблоны `claim`
добавляют только один дешёвый браузерный критерий — «страница открывается без ошибок в консоли»;
селекторы эвристика не выдумывает, иначе проверка проверяла бы саму себя.

## LLM (необязательно)

Без ключа работают офлайн-шаблоны: одинаковый ввод → одинаковые критерии.

```bash
export WITNESS_LLM_KEY=...          # ключ приносите свой
export WITNESS_LLM_URL=...          # любой OpenAI-совместимый endpoint
export WITNESS_LLM_MODEL=gpt-4o-mini
```

Ответ модели валидируется схемой; при любой ошибке — тихий откат к шаблонам.
Код и результаты никуда не отправляются.

## История прогонов

Прогоны лежат в `.witness/witness.db`. Это SQLite, но драйвер встроен в Node (`node:sqlite`),
поэтому npm-зависимостей не появилось. Таблица `runs` хранит сводные поля, полный JSON прогона
и SHA-256 хеш — последний проверяет `witness badge --verify`.

Если в проекте остались старые `.witness/runs/*.json` (версия до SQLite), они импортируются
при первом обращении и **не удаляются** — остаются архивом.

Плата за это решение названа честно: база бинарная, `git diff` по ней нечитаемый, а ветки
с разными прогонами дадут конфликт при слиянии. Человекочитаемый след — `report.html`
и `badge.json`; они лежат рядом и всегда пересобираются из базы.

## Что внутри

```
bin/witness.js        точка входа (в репозитории)
src/cli.ts            разбор аргументов, команды
src/core/             критерии, http- и браузерные проверки, ledger, differential, tamper, отчёт, badge
src/commands/         init, claim, run, report, badge, wrap
vscode/               тонкая обёртка для VS Code
examples/shop/        учебный проект
eval/golden/          golden-набор: 20 задач, сервер broken/fixed, харнесс метрик
scripts/build.mjs     сборка dist/ для npm (встроенный stripTypeScriptTypes)
skills/witness/       навык для агента (OpenCode, Claude Code, aitmpl)
test/                 85 тестов на node:test
```

В репозитории сборки нет — Node исполняет TypeScript напрямую. Для npm `prepare`
собирает `dist/`: Node запрещает type stripping для файлов внутри `node_modules`,
поэтому опубликованный пакет содержит обычный JavaScript.

```bash
node --test
npm run golden
```

## Golden-набор

`npm run golden` поднимает одно приложение в двух состояниях — `broken` (фичи нет)
и `fixed` (фича есть) — и прогоняет 20 задач. Для каждой: `claim` → `run --baseline`
на broken → `run` на fixed.

Замер на 16.11.2026:

| Метрика | Результат |
|---|---|
| false-green (broken сказал «прошло») | **0/20** |
| negative-green (непроверяемая задача сказала «прошло») | **0/7** |
| positive false-red (фича есть, проверка упала) | **0/13** |
| тавтологии (зелёные и на базе) | 10 — по одной на csv/api |
| машинные критерии | 40/70 |

Набор v1 покрывает HTTP-путь; браузерные кейсы в него не входят. Цифры — измерение
на фиксированном наборе, а не гарантия для любого проекта. Подробности:
`eval/golden/last-report.json`.

## Границы

- **Всегда:** человек утверждает критерии; артефакты остаются локально; дифференциал обязателен.
- **Никогда:** не считать зелёным критерий, не падающий на базе; не править тесты пользователя;
  не отправлять код на сервер без согласия.
- **Пока нет:** Docker-изоляции, скриншотов и видео-трейсов, облачных прогонов, командного дашборда.

## Метрика доверия

**False-green rate < 1%** — доля случаев, когда Witness сказал «прошло», а на самом деле не работало.
Всё остальное в продукте подчинено этой цифре. На golden-наборе v1 — **0/20**.
Это не гарантия: набор покрывает HTTP-путь и фиксированные задачи, его нужно расширять
вместе с продуктом.
