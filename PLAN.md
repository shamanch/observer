# PLAN: Witness — как строим MVP

**Версия:** 0.1 · **Дата:** 16.11.2026 · **Основание:** `SPEC.md` v0.2
**Статус:** Phase 2 (Plan) — утверждено к исполнению

---

## 1. Что должно работать к концу MVP

Один пользовательский путь, целиком, без Docker и без API-ключей:

```bash
cd мой-проект
npx witness init                          # .witness/ + конфиг + первый прогон окружения
npx witness claim "Экспорт отчёта в CSV"  # 3–7 критериев, человек правит и утверждает
# ... агент работает ...
npx witness run                           # pass/fail по каждому критерию + отчёт + badge-данные
```

Плюс два расширения пути:

```bash
npx witness run --all      # регрессия по всему ledger
npx witness badge          # SVG + badge.json для README
```

Если этот путь работает на реальном Next.js-проекте за < 5 минут — MVP состоялся.

## 2. Ключевые технические решения

| Решение | Выбор | Почему |
|---|---|---|
| Runtime | Node 24 + `--experimental-strip-types` | ноль сборки, ноль зависимостей на старте, мгновенный TTFV |
| Зависимости | **ноль** в MVP-ядре | установка за секунды; Playwright подключается лениво, только если у пользователя есть `browser`-критерии |
| Хранение | SQLite через встроенный `node:sqlite` (`.witness/witness.db`) | история и быстрый поиск без внешней зависимости; JSON-прогоны импортируются, остаются архивом |
| Критерии | YAML/JSON в `.witness/claims/<id>.json` | машинно-читаемо, правится человеком, версионируется |
| LLM | **BYO-ключ** + офлайн-шаблоны | без ключа `claim` работает на эвристиках; LLM — улучшение, не требование |
| Проверки | `http` (в MVP) → `playwright` (следующий шаг) | HTTP-проверка даёт вертикальный срез без браузера |
| Отчёт | статический HTML + JSON, без сервера | `witness report` пишет файл, открывается как файл — нет порта |
| Badge | SVG + `badge.json` с SHA-256 ledger | проверяемо офлайн, публикуется куда угодно |
| VS Code | отдельный пакет `vscode/`, вызывает CLI | нет дублирования логики, расширение падает, ядро живо |

**Решения по двум новым вопросам из SPEC §11 (закрыты 16.11.2026):**
1. LLM — BYO-ключ (`WITNESS_LLM_KEY` / `OPENAI_API_KEY`), при отсутствии — детерминированные шаблоны по ключевым словам задачи. Продукт обязан работать без интернета.
2. История — SQLite в `.witness/witness.db` через встроенный `node:sqlite`. Внешних зависимостей нет. Старые `.witness/runs/*.json` импортируются при первом обращении и остаются архивом.
   Плата за решение: база бинарная, дифф в git нечитаемый. Поэтому рядом с базой по-прежнему лежат `report.html`, `badge.json` и `baseline.json` — они и есть человекочитаемый след.

## 3. Порядок реализации (6 срезов)

Каждый срез заканчивается работающей командой и тестом. Не переходим дальше, пока срез не зелёный.

### Срез 1. Скелет и `init` (фундамент)
- `package.json` (type: module, bin), `tsconfig.json`, `README.md`
- `bin/witness.js` → `src/cli.ts`
- `src/commands/init.ts`: создаёт `.witness/`, `witness.json`, `.gitignore`-строку, делает первый `env probe`
- `src/core/config.ts`: чтение/валидация конфига
- **Проверка:** `witness init` в пустой папке создаёт 4 файла, повторный запуск не ломает.

### Срез 2. `claim` и модель критериев (сердце продукта)
- `src/core/criteria.ts`: схема критерия, парсер из текста задачи (эвристики + опциональный LLM)
- `src/commands/claim.ts`: генерирует черновик → показывает → ждёт подтверждения (`--yes` для CI)
- `src/core/llm.ts`: BYO-ключ, строгий JSON-ответ, деградация к шаблонам
- **Проверка:** `witness claim "..."` создаёт `.witness/claims/<id>.json` с 3–7 критериями; тесты на парсер (10 кейсов).

### Срез 3. `run` и исполнитель HTTP-проверок (доказательство)
- `src/core/runner.ts`: последовательный прогон, таймауты, запись результата
- `src/checks/http.ts`: GET/POST, статус, заголовки, JSON-assertions, подстроки в теле
- `src/commands/run.ts`: `--all`, `--claim <id>`, `--base <ref>` (differential)
- `src/core/ledger.ts`: append-only история в SQLite (`node:sqlite`), хеш прогона, импорт старых JSON
- **Проверка:** на тестовом HTTP-сервере 4 критерия → 3 pass / 1 fail; `--base` помечает тавтологичные критерии.

### Срез 4. Differential и anti-tamper (защита доверия)
- `src/core/differential.ts`: прогон на базовом состоянии, правило «критерий обязан падать на базе»
- `src/core/tamper.ts`: анализ `git diff` — `skip`, `.only`, удалённые assertion, правки CI, `--no-verify`
- **Проверка:** тест «критерий зелёный и на базе» → вердикт `tautology`; тест «агент удалил тест» → `tamper.detected`.

### Срез 5. `report` и `badge` (видимость и вирусность)
- `src/core/report.ts`: генерация самодостаточного `report.html` (inline CSS, без сети)
- `src/core/badge.ts`: SVG shields-стиля + `badge.json` (hash, counts, дата, версия)
- `src/commands/report.ts`, `src/commands/badge.ts`
- **Проверка:** отчёт открывается двойным кликом, badge рендерится в README; `badge.json` меняется при изменении ledger.

### Срез 6. `wrap` и VS Code-обёртка
- `src/commands/wrap.ts`: запускает команду агента, затем автоматически `run --all`
- `vscode/`: `package.json`, `extension.ts` (3 команды: Init / Claim / Run, вывод в Output Channel)
- **Проверка:** `witness wrap -- node -e "console.log(1)"` выполняет команду и прогон; расширение активируется и вызывает CLI.

## 4. Что НЕ делаем в MVP (и почему)

| Отложено | Причина |
|---|---|
| Docker-изоляция | барьер входа; локальный процесс + таймауты достаточны для первого доверия |
| Playwright в зависимостях ядра | браузер ~300 МБ; подключается opt-in, HTTP-путь остаётся нулевым по установке |
| Облачные прогоны | монетизация после того, как локальный продукт стал привычкой |
| Внешняя СУБД (Postgres, сервер) | встроенного `node:sqlite` хватает локально; синхронизация — не задача MVP |
| Своя LLM | BYO-ключ + шаблоны; модель — не наше конкурентное преимущество |
| Дашборд, аккаунты, биллинг | не влияет на false-green rate |

---

## 5. Риски и что делаем заранее

| Риск | Ранний сигнал | Действие |
|---|---|---|
| Эвристики `claim` дают мусорные критерии | пользователь всё переписывает руками | 20 golden-задач; цель — ≥60% критериев приняты без правок |
| HTTP-проверок мало для реальных фич | «у меня SPA, мне нужен браузер» | Playwright — срез 7 сразу после MVP, не позже |
| Хрупкость проверок | падения без изменения кода | только стабильные assertions; `--base` ловит ложные |
| Ноль зависимостей усложняет HTTP-клиент | баги в парсинге | `node:fetch` + `node:test` на каждый edge case |
| Badge подделывается | кто-то рисует SVG руками | badge содержит hash ledger, проверяется командой `witness badge --verify` |
| Тонкая VS Code-обёртка не нужна | ей не пользуются | CLI первичен; расширение не блокирует релиз |

## 6. Чекпоинты (go / no-go)

| # | После среза | Критерий прохода |
|---|---|---|
| C1 | 1 | `init` идемпотентен, `node --test` зелёный |
| C2 | 2 | 10/10 тестов парсера; `claim` работает без ключа LLM |
| C3 | 3 | Сквозной путь на реальном проекте < 5 минут |
| C4 | 4 | Тавтология и tamper ловятся тестами |
| C5 | 5 | Отчёт и badge открываются без сети |
| C6 | 6 | `wrap` не ломает exit-код агента; расширение собирается |

**No-go условие:** если после C3 сквозной путь занимает > 10 минут или требует ручной правки конфигов — останавливаемся и чиним TTFV, а не идём вширь.

---

## 7. Метрики, которые меряем с первого дня

- **false-green rate** — на golden-наборе (20 задач: 10 должны пройти, 10 упасть).
- **TTFV** — время от `init` до первого `run` с результатом.
- **Доля критериев, принятых без правок** — качество `claim`.
- **Количество проверок в ledger через 7 дней** — признак привычки.

Пишем их в `.witness/runs/*.json` с самого начала: без данных нельзя доказать, что продукт работает.

## 8. Результаты MVP (16.11.2026)

**Тесты:** `node --test` → 57 тестов, все проходят (~3,5 с).

| # | Чекпоинт | Результат | Доказательство |
|---|---|---|---|
| C1 | `init` идемпотентен | **пройден** | `test/cli.test.ts`: повторный `init` не меняет mtime конфига |
| C2 | 10/10 задач парсера, `claim` без ключа LLM | **пройден** | `test/claimgen.test.ts` (10 задач, все валидны); `claim` печатает «источник: шаблоны (без LLM)» |
| C3 | Сквозной путь < 5 минут | **пройден** | `examples/shop`: init + claim = 0,7 с; run + report + badge = 1,0 с |
| C4 | Тавтология и tamper ловятся | **пройден** | `run --baseline` → все три http-критерия помечены тавтологией; в git-фикстуре найдены удалённый assert, `skip`, новый `.github/workflows/ci.yml` |
| C5 | Отчёт и badge без сети | **пройден** | `report.html` — 4,2 КБ, 0 совпадений `https?://`; `badge --verify` → ok |
| C6 | `wrap` сохраняет exit-код; расширение валидно | **пройден** | `wrap -- node -e "process.exit(3)"` → exit 3, прогон выполнен; `node --check vscode/src/extension.cjs` → ок |

**Отрицательные проверки (продукт должен уметь говорить «нет»):**

- Сервер `examples/shop` остановлен → `run` даёт exit 1, три критерия падают с «нет соединения с …», в differential — три регрессии.
- В git-фикстуре агент заменил тест на `skip` и добавил новый CI-файл → anti-tamper выдал 2 × КРИТИЧНО + 1 × внимание.
- `wrap` при падении агента (код 3) всё равно выполняет прогон, но возвращает 3 — код агента важнее.

**Что осталось непроверенным:**

- Запуск расширения внутри реального VS Code (нужен Extension Development Host) — проверен только синтаксис.
- Реальный LLM-путь `claim` (нет ключа в окружении) — откат к шаблонам проверен, сетевой вызов нет.

**Итог по no-go условию:** TTFV укладывается в секунды, ручная правка конфигов нужна только при нестандартном порте → идём дальше, не чиним TTFV.

## 9. Второй раунд (16.11.2026): SQLite и браузерные проверки

Решения пользователя: LLM — BYO-ключ (без изменений), история прогонов — SQLite.

**Сделано:**

- `src/core/ledger.ts` переписан на встроенный `node:sqlite`: таблица `runs` хранит сводные поля, полный JSON прогона и SHA-256. Внешних зависимостей не прибавилось.
- Старые `.witness/runs/*.json` импортируются при первом обращении, не удаляются и повторно не дублируются.
- Чтение не создаёт файл базы: `report` и `badge` на пустом проекте не оставляют пустой `witness.db`.
- `src/core/browser.ts`: `check.type: "browser"` — `visible`, `text`, `consoleErrors`, шаги `click`/`fill`. Playwright грузится лениво, в `dependencies` его нет.
- `claim` для UI-задач добавляет ровно один браузерный критерий — «страница открывается без ошибок в консоли». Селекторы эвристика не выдумывает.
- 73 теста, включая фейковый браузерный драйвер: 300 МБ в CI не нужны.

**Проверено вживую:** `examples/shop` — 2 прогона в `witness.db` (28 КБ), отчёт 4,7 КБ без внешних ссылок, `badge --verify` ok. Без Playwright браузерный критерий даёт `error` с точной командой установки, exit 1.

**Не проверено:** реальный запуск Chromium (пакет не устанавливался) и импорт JSON на настоящем старом проекте (только фикстура в тесте).

**Честная цена SQLite:** база бинарная — `git diff` по ней нечитаемый, параллельные ветки с разными прогонами конфликтуют. Человекочитаемый след — `report.html` и `badge.json`.
