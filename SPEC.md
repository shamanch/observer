## 1. Objective

**Что строим.** Инструмент, который превращает задачу, отданную AI-агенту, в **исполняемую проверку** и хранит её как регрессионный тест. После работы агента вы получаете не «готово» от модели, а видео и pass/fail по каждому критерию приёмки — полученные детерминированным прогоном, а не вторым LLM.

**Почему.** В 2026 году узкое место сместилось: код пишется быстрее, чем проверяется. Люди перестали верить слову «done», но у них нет ни тестов, ни времени их писать.

**Пользователь.** «Вайбкодер» с работающим продуктом и без QA: соло-фаундер, инди-хакер, небольшая студия, которая сдаёт проекты клиентам.

**Успех продукта (12 мес).** 2 000 активных установок CLI, 300 платящих, ~$3k MRR, и главное — **false-green rate < 1%** (доля случаев, когда мы сказали «работает», а оно не работало).

**Успех пользователя.** «Я больше не проверяю руками каждую фичу» + через месяц у него в репозитории лежит 20–60 тестов, которых он не писал.

## 2. Проблема и доказательства

### 2.1. Что происходит

Агент пишет код, сообщает «готово, тесты проходят», человек мержит. Через день выясняется: фича не работает в реальном сценарии, часть тестов агент ослабил, а регрессия всплывает у клиента.

### 2.2. Сигналы спроса (собраны 15.11.2026)

**Объём категории:**
- `@openai/codex` — 26,5 млн скачиваний/неделю (npm)
- `@anthropic-ai/claude-code` — 17,6 млн/неделю
- `opencode-ai` — 3,9 млн/неделю

**Громкость боли (Hacker News, points / comments):**
- «Issue: Claude Code is unusable for complex engineering tasks with Feb updates» — **1364 / 753** (апр 2026)
- «After two years of vibecoding, I'm back to writing by hand» — **865 / 634** (янв 2026)
- «Vibe coding and agentic engineering are getting closer than I'd like» — **787 / 885** (май 2026)
- «There is an AI code review bubble» — **351 / 249** (янв 2026)
- «Humble Bundle just killed most of their security through vibecoding» — **413 / 236** (ноя 2026)
- «PS3 Emulator Devs Politely Ask That People Stop Flooding It with AI PRs» — **189 / 148** (май 2026)

**Прямые формулировки боли (HN, цитаты):**
- «the loop is only as good as the verifier, and agents are very good at finding the gap between "passes the check" and "is correct"» (окт 2026)
- «unit tests pass per agent, but the seams break at merge» (апр 2026)
- «agents keep making regressions and breaking rules. They'll even take shortcuts» (май 2026)
- «A regulator or auditor can't trust a log produced by the same operator who runs the agent» (ноя 2026)
- «I created 50+ projects with a sleek UI, but I could not explain any of them» (авг 2026)

**Что уже пробовали и почему не помогло:**
- Трекеры расходов (ccusage — 341 тыс. скачиваний/нед) решают «сколько», но не «работает ли».
- AI-ревью PR (CodeRabbit, 20 тыс. клиентов) проверяет **код**, а вывод делает **та же LLM** → «AI reviewing AI».
- OSS-поделки «verify agent claims» (45 репозиториев по запросу GitHub) — все по 0–2 звезды, без differential-проверки и без хранения результатов.

### 2.3. Почему сейчас

1. Агенты стали массовыми (десятки миллионов установок), но **PR-процесс не обязателен** — люди работают прямо в репозитории, и CodeRabbit туда не достаёт.
2. Стоимость ошибки выросла: вайбкоднутые проекты пошли в прод (кейс Humble Bundle, ноябрь 2026).
3. Второй LLM в роли проверяющего дискредитирован («AI code review bubble») — рынок готов к детерминированной проверке.

## 3. Решение: как это работает

Три шага, каждый — одна команда.

### Шаг 1. Claim — контракт до работы агента

```bash
witness claim "Добавить экспорт отчёта в CSV на странице /reports"
```

Witness разбирает формулировку и предлагает **3–7 проверяемых критериев**:

```
1. На /reports есть кнопка «Экспорт CSV»
2. Клик скачивает файл с расширением .csv
3. Файл содержит строку заголовков и N строк данных текущего отчёта
4. У пользователя без прав экспорт возвращает 403
```

Человек правит/подтверждает. **Критерии утверждает человек, а не модель.** Это ключевое: контракт — источник истины, а не догадка LLM.

### Шаг 2. Witness — исполняемая проверка

После работы агента:

```bash
witness run
```

Что происходит:
1. Поднимается окружение из репозитория (`docker compose up` или `npm run dev`), в изоляции.
2. Под каждый критерий генерируется **Playwright-сценарий или HTTP-вызов** — один раз.
3. Сценарий прогоняется на **текущем** коде и на **базовом** (git stash / предыдущий коммит).
4. Записываются `trace.zip`, видео, скриншоты, сетевые логи.

Результат в терминале и в локальном отчёте:

```
✓ 1. Кнопка «Экспорт CSV» присутствует          PASS  (312 ms)
✓ 2. Клик скачивает .csv                        PASS  (1.4 s)
✗ 3. Файл содержит заголовки и N строк          FAIL  — файл пустой (см. видео 00:12)
✓ 4. Без прав → 403                             PASS  (98 ms)

Differential: критерий 3 падает и на базе, и на текущем коде
→ проверка не доказала фикс (возможен пустой тест)
```

### Шаг 3. Ledger — регрессионный набор, которого у пользователя не было

Каждая проверка сохраняется в `.witness/*.spec.ts` и в git. При следующем изменении все проверки прогоняются автоматически:

```bash
witness run --all
→ 47 проверок, 46 pass, 1 fail (регрессия в /reports)
```

Через месяц у человека 40–60 тестов. Он их не писал — они появились как побочный продукт проверки.

### 3.1. Три механики, которые делают продукт лучшим, а не «ещё одним»

**① Детерминизм.** LLM участвует только в генерации сценария — один раз, с ревью человеком. Дальше это обычный Playwright-код. Значит: воспроизводимо, дёшево (нет токенов на каждый прогон), не деградирует вместе с моделью. Прямое контр-позиционирование к «AI reviewing AI».

**② Differential-проверка.** Каждая проверка обязана **падать на базовой версии**. Если критерий зелёный и до фикса — это не проверка, а тавтология (агенты это делают постоянно: «тест проходит» потому, что ничего не проверяет). Ни один конкурент этого не делает явно.

**③ Anti-tamper.** Отдельный отчёт, если агент в процессе «починил» проверку, а не код: удалил/заскипал тест, ослабил assertion, поправил CI, добавил `--no-verify`. Это ловит самый частый способ имитации успеха.

### 3.2. Что видит человек

Самодостаточный отчёт `.witness/report.html` (открывается как файл, без локального сервера):
- список критериев с pass/fail и временем;
- видео прохождения — в следующем срезе (Playwright), в MVP: текстовые доказательства и ответы API;
- differential: какие критерии падали на базе, а какие были зелёными и там (тавтологии);
- секция «подозрительно»: удалённые assertion, `skip`, правки CI, `--no-verify`.

## 5. Scope MVP

### Входит (6 недель)
- CLI на TypeScript: `init`, `claim`, `run`, `ledger`, `report`, `badge`, `wrap`
- **VS Code-расширение** (тонкая обёртка): «Claim → Run → показать отчёт» в боковой панели
- Генерация Playwright/HTTP-сценариев из подтверждённых критериев
- Запуск в Docker-изоляции, подъём окружения из `compose` или npm-скрипта
- Differential-прогон (текущий vs базовый коммит)
- Anti-tamper отчёт (тесты/CI/конфиги в диффе)
- Локальный отчёт с видео и трейсами
- Хранение `.witness/` в репозитории, прогон всех проверок
- Публичный `witness badge` (SVG + `badge.json` с хешем ledger)
- Интеграция-обёртка: `witness wrap "claude"` — запускает агента и сразу проверяет

### Не входит
- Мобильные и десктоп-приложения
- Хостинг, командные дашборды, SSO, enterprise
- Ревью качества кода (не наш продукт)
- Собственная LLM-модель
- Поддержка 10 языков/фреймворков (только web + HTTP в MVP)

### Архитектура

```
witness (CLI, TS)
├─ core/       критерии, ledger, badge, differential, tamper (без UI)
├─ claim/      разбор задачи → критерии (LLM, один раз)
├─ generate/   критерий → Playwright/HTTP spec (LLM, один раз)
├─ runner/     docker-изоляция или локальный процесс, прогон, запись trace
├─ differ/     прогон на базовом коммите, сравнение результатов
├─ tamper/     статический анализ диффа: тесты, CI, конфиги, skip
├─ ledger/     .witness/*.spec.ts + report.json
├─ badge/      SVG + badge.json с хешем ledger
└─ report/     статический HTML без сервера (один файл)

vscode/ (тонкая обёртка)
├─ вызывает CLI, не дублирует логику
└─ панель: claim → run → отчёт/видео
```

Стек: TypeScript (Node 24, type stripping — без сборки), `node:sqlite` (история), Playwright (opt-in для браузерных проверок), статический HTML (отчёт). Внешних зависимостей в ядре нет: разбор аргументов, схема критериев и HTML пишутся вручную.

### Команды

```
witness init                     # инициализация в репозитории
witness claim "<задача>"         # критерии приёмки, ревью человеком
witness run                      # проверка текущего состояния
witness run --all                # все проверки (регрессия)
witness report --open            # локальный отчёт
witness badge                    # SVG + badge.json для README
witness wrap -- <agent-cmd>      # агент + авто-проверка
```

### Тестирование (своего продукта)
- Юнит: разбор критериев, tamper-правила, differ-логика — Vitest, покрытие >80%.
- Интеграция: прогон против 3 эталонных репозиториев (Next.js SSR, Vite SPA, Express API).
- Golden-тесты: 20 задач с известным результатом (10 «должно пройти», 10 «должно упасть») — метрика false-green.

## 6. Границы

**Всегда:** изоляция прогонов в контейнере; человек подтверждает критерии; все артефакты остаются локально; differential обязателен.
**Спросить сначала:** установка Docker-образа; запись в `.witness/`; сетевые вызовы к LLM.
**Никогда:** не отправлять код на сервер без согласия; не считать «зелёным» критерий, не падающий на базе; не редактировать тесты пользователя автоматически.

## 9. Метрики

- **False-green rate** < 1% — главная метрика доверия.
- TTFV (первый успешный `run`) < 5 минут.
- Доля задач, где человек подтвердил критерии: > 70%.
- Проверок в репозитории через 30 дней: медиана ≥ 20.
- W4 retention ≥ 35%.

## 10. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| CodeRabbit добавит исполнение проверок | средняя | локальность, до-PR сегмент, скорость, фокус на «нет тестов» |
| Playwright-сценарии хрупкие | высокая | селекторы по ARIA/ролям; авто-ремонт только с подтверждением; pin окружения |
| Агент генерирует проверку под себя | средняя | differential + утверждение критериев человеком + anti-tamper |
| Сегмент «соло» не платит | средняя | Team-план и агентства; доказательство для клиента |
| Docker-барьер на входе | средняя | режим без Docker (локальный процесс) для первого запуска |
